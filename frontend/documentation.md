# Frontend Documentation

## Overview

Daymark is the Next.js frontend for the Calendar Assistant backend. It provides:

- Google sign-in and session-aware routing
- A responsive workspace with Agent and Calendar views
- Chat requests that preserve the backend `thread_id`
- Explicit approve/reject controls for calendar-changing actions
- Recent conversation activity
- A month navigator for the calendar surface

The backend currently exposes calendar access through the assistant tools, but does not expose a calendar event-listing HTTP endpoint. The Calendar view therefore shows the month structure without inventing event data and directs schedule questions to the assistant.

## Project Structure

```text
app/
  auth/
    callback/
      page.tsx          OAuth callback status and retry screen
  components/
    AuthScreen.tsx      Unauthenticated Google sign-in screen
    CalendarView.tsx    Month grid and calendar handoff state
    ChatView.tsx        Conversation, approval controls, and activity
    LoadingScreen.tsx   Shared loading state
    Sidebar.tsx         Agent and Calendar navigation
    Topbar.tsx          Branding and account menu
    Workspace.tsx       Authenticated UI state and orchestration
  lib/
    api.ts              Typed fetch wrappers for backend endpoints
    calendar.ts         Calendar date calculations and labels
    types.ts            Shared frontend/backend response types
  globals.css           Shared visual system and responsive layout
  layout.tsx            Metadata and application root
  page.tsx              Authentication gate and workspace entry point
```

`page.tsx` owns only the initial session check. `Workspace.tsx` owns authenticated interaction state. Presentation and endpoint details live in components and `lib/`, which keeps the main route small and makes each surface independently testable.

## Backend Contract

The frontend uses the endpoints defined in `backend/src/api.py`:

| Frontend action | Method | Endpoint                     | Purpose                                       |
| --------------- | ------ | ---------------------------- | --------------------------------------------- |
| Check session   | `GET`  | `/auth/me`                   | Decide whether to show login or the workspace |
| Start sign-in   | `GET`  | `/auth/google/login`         | Begin the backend-owned Google OAuth flow     |
| End session     | `POST` | `/auth/logout`               | Clear the backend session                     |
| Chat            | `POST` | `/chat`                      | Send a message, optionally with `thread_id`   |
| Approve/reject  | `POST` | `/chat/{thread_id}/approval` | Resume a pending calendar change              |

All requests use `credentials: 'include'` because the backend stores the signed-in identity in a session cookie.

## OAuth Callback Fix

The backend redirects successful or failed Google sign-in to:

```text
http://localhost:3000/auth/callback?google_auth=success
http://localhost:3000/auth/callback?google_auth=error&error=...
```

The frontend now has an App Router page at `app/auth/callback/page.tsx`, so this URL is no longer a 404. It checks the callback result, verifies `/auth/me` after success, and displays a retry action for errors.

`Invalid OAuth state` is generated by the backend before Google credentials are exchanged. In `backend/src/api.py`, the callback compares the returned OAuth `state` parameter with `request.session['oauth_state']`. The error means the temporary backend session cookie was not returned, was overwritten, or the OAuth flow was started in a different browser context.

The backend also uses Google's PKCE flow. The authorization request creates a `code_verifier`; the backend stores it in the signed session as `oauth_code_verifier` and restores it when exchanging the callback code. The OAuth request also includes OpenID identity scopes. After the token exchange, the backend verifies Google's signed ID token to obtain the user's `sub` and email, instead of making a separate unauthorised userinfo request. Without the PKCE handoff, Google returns `invalid_grant: Missing code verifier`; without identity scopes, the profile lookup cannot authenticate.

Check these settings when testing locally:

1. Start the Google login from `http://localhost:3000`, not from a copied Google URL.
2. Use the same host consistently. Do not begin on `127.0.0.1` and finish on `localhost`.
3. Run the backend with `FRONTEND_URL=http://localhost:3000` and include `http://localhost:3000` in `FRONTEND_ORIGINS`.
4. Use the redirect URI configured in Google Cloud: `http://localhost:8000/auth/google/callback`.
5. Allow cookies in the browser and avoid private browsing extensions that clear localhost cookies.
6. If a previous flow was abandoned, return to the app and start a fresh login rather than reusing the old callback URL.

7. Restart the backend after applying OAuth changes, then start a fresh login. Do not reuse a callback URL from an earlier attempt.

The frontend can display the error and retry, but it cannot repair a missing backend session cookie. The session middleware and OAuth state are intentionally owned by the backend.

## Configuration

Create `frontend/.env.local` when the backend is not at its default address:

```text
NEXT_PUBLIC_API_URL=http://localhost:8000
```

The backend must separately be configured as described in `backend/README.md`, especially `FRONTEND_URL`, `FRONTEND_ORIGINS`, `SESSION_SECRET`, and Google OAuth credentials.

## Local Development

From the `frontend` directory:

```powershell
npm install
npm run dev
```

Open `http://localhost:3000`. For a production check:

```powershell
npm run lint
npm run build
```
